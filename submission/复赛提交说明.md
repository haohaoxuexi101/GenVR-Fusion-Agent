## 2. Scientific Finding & Environment Definition Report

Report requirements:

## 1. 科学问题与发现目标

## 1. Scientific Problem & Discovery Objectives

研究的科学问题是什么？为什么值得研究？希望Agent 发现什么类型的新规律、新信号、新结构或新假设？最终声称的核心科学发现（ScientificClaim）是什么？What is the target scientific problem? Why is it worth investigating? What newpatterns, signals, structures or hypotheses are expected to be discovered by the

Agent? What is the core scientific claim put forward in your work?

## 2. Environment / Benchmark 定义

## 2. Environment / Benchmark Definition

• Agent 能观察什么（Observation）、执行什么操作（Action）、调用哪些工具（Tools）？

用了哪些数据、模拟器、实验环境、数据库或外部资源？

• 怎么判断一次发现成立——评价指标、Verifier、GroundTruth还是别的验证机制？

• 如果存在隐藏答案、测试集或 Ground Truth，必须明确哪些信息Agent 可见/不可见，避免信息泄漏。

• What Observations can the Agent obtain, what Actions can it perform, and which Tools can it invoke?

• What datasets, simulators, experimental environments, databases or external resources are adopted?

How is a valid discovery judged: via evaluation metrics, Verifier, Ground Truth or other validation mechanisms?

If hidden answers, test sets or Ground Truth are present, explicitly define information visible / invisible to the Agent to prevent information leakage.

## 3. Agent 如何完成发现

## 3. Agent Discovery Workflow

总体架构和工作流程：如何提出假设、调用工具、跑实验或分析数据、修正判断、得到结论。

Overall architecture and workflow: how hypotheses are generated, tools invoked, experiments executed or data analyzed, judgments revised, and final conclusions

reached.

报告要能和提交的 trajectory / log 对应上，让评审能追溯「发现是怎么产生的」。 The report shall align with submitted trajectories / logs so that judges can trace how discoveries are generated.

如果正式运行中存在人工干预、结果筛选、Best-of-N 或多次重跑，必须如实说明。 If manual intervention, result filtering, Best-of-N sampling or multiple re-runs are applied in official executions, such facts must be truthfully documented.

## 4. 发现结果与验证

## 4. Discovery Outcomes & Validation

给出核心发现和主要证据，并说明独立验证、重复实验、不同随机种子、对照实验或稳健性检验。

Present core findings and key supporting evidence. Describe independent validation, repeated experiments, tests with different random seeds, control-group experiments and robustness checks.

对随机性强的Agent，不要求逐token 或逐action 完全一致，但要说明发现的稳定性、成功率和主要波动。

For Agents exhibiting high stochasticity, exact token-by-token or action-by-action replication is not required. Document discovery stability, success rates and major fluctuation patterns.

简要说明当前发现最主要的 limitation 和可能的 false positive。Briefly state major limitations and potential false positive risks of currentfindings.

## 三、代码类材料

## IV. Code Materials

## 1. 三类核心复现材料

## 1. Three Core Reproducibility Materials

开放探索赛题需提交以下三类核心复现材料，缺一项即为材料不完整：

The Open Exploration Sub-track requires submission of all three core reproducibility materials. Missing any one will render the submission incomplete.

①最小可运行探索环境——不要求功能齐全，但要能装、能跑、能复现你报告里的核心结果。README要写清环境安装、依赖、配置方法、关键版本和预期输出。

① Minimal Operable Exploration Environment: Full feature completeness is not mandatory, but the environment must be installable, runnable, and capable of reproducing core results described in the report. The README shall clearly document environment installation, dependencies, configuration approaches,

key versions and expected outputs.

②至少一次完整探索日志——与正式结果对应的完整运行记录。至少能追溯：Agent输入与 observation、输出与 action、tool call 及返回、环境反馈、关键中间产物、最终结果与指标、必要的错误与重试。推荐JSON /JSONL，不要只交截图或录屏。

② At Least One Complete Exploration Log: Full runtime record corresponding to official results. It shall at minimum trace: Agent inputs and Observations, outputs and Actions, tool-call payloads and returns, environment feedback, key intermediate artifacts, final results and metrics, as well as relevant error and retry events. JSON / JSONL is preferred. Screenshots or screen recordings alone are not acceptable.

③参照系设计——需证明「发现」并非随机波动带来的偶然结果。参照系可以是随机探索、平凡解或简单基线，并需提交对应结果供评审对比。

③ Reference Benchmark Design: Prove that findings are not accidental artifacts caused by random fluctuations. Reference benchmarks may include random exploration runs, trivial solution baselines or simple baselines. Corresponding outputs shall be provided for judge comparison.

## 2. 仓库的最低要求

## 2. Minimum Repository Requirements

不强制统一项目结构，但必须满足：

No unified project structure is enforced, yet all below requirements must be satisfied:

1. README要让评审知道「怎么跑」——环境与依赖安装、数据如何获得、用的模型/API及关键配置、大致算力与成本、smoketest怎么跑、核心结果怎么复现、跑成功应得到什么输出。

1. The README shall enable judges to execute the workflow: environment and dependency installation, data acquisition, model / API selections and key

configurations, approximate compute resource and cost estimates, smoke test procedures, core-result reproduction steps, and expected successful outputs.

2. 完整 trajectory / log——至少能追溯：Agent 输入与 observation、输出与action、tool call 及返回、Environment feedback、关键中间产物、最终结果与指标、必要的错误与重试信息。

2. Complete trajectories / logs: At minimum trace Agent inputs & Observations, outputs & Actions, tool-call requests & returns, environment feedback, key intermediate artifacts, final results & metrics, plus necessary error and retry records.

推荐JSON/JSONL等机器可解析格式，不要只交截图或终端录屏。模型平台无法导出的privatereasoning不作要求，但Agent 实际接收到和实际执行的内容必须完整保存。

Machine-parsable formats such as JSON / JSONL are recommended; screenshots or terminal recordings alone are invalid. Private reasoning that cannot be exported by model platforms are exempt, yet content actually received and executed by the Agent must be fully preserved.

3. 可复现配置——依赖与环境、模型名称与版本、主要sampling参数、randomseed、数据版本、正式结果对应的 run / config、第三方代码来源及License。不得上传 API Key、密码或其他 secret。

3. Reproducible configurations: Dependencies and environment settings, model names and versions, primary sampling parameters, random seeds, dataset versions, run / config corresponding to official results, third-party code origins and licenses. Do not upload API keys, passwords or other secrets.

4. 数据与自建Benchmark——公开数据建议提供自动下载/预处理脚本；自建benchmark 需开源关键构建流程并提供可访问的数据或稳定引用。因版权、隐私或许可不能公开的部分，要在报告和README中说明其对复现的影响。

4. Datasets & Self-Built Benchmarks: Provide automatic download / pre-processing scripts for public datasets. For self-built benchmarks, open-source key construction workflows and supply accessible data or stable references. For components that cannot be released due to copyright, privacy or licensing restrictions, document their impact on reproducibility within both report and README.

评审口径：问题定义与环境设计占45%。开放探索赛题不仅关注发现本身，也关注问题定义是否合理、环境是否可运行、评估口径是否清楚。负结果可以提交，但需说明失败原因及其价值。

Judging Remarks: Problem Definition & Environment Design accounts for 45 % of total weight. The Open Exploration Sub-track evaluates not only final discoveries themselves, but also the rationality of problem definition, environment operability and clarity of evaluation methodology. Negative-result submissions are acceptable provided failure causes and their research value are

explained.
